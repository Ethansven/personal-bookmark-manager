# Session 04 — 2026-07-27 — end-to-end smoke + PKCE verification

## MCP verification log

Booted both services:
- backend: `node dist/src/main.js` on :3000 with placeholder `AUTH0_ISSUER=http://127.0.0.1:9999` and `AUTH0_AUDIENCE=https://bbl-candidate-test-api` (real tenant would be `https://dev-yg.us.auth0.com/`).
- frontend: `vite --port 5173 --host 127.0.0.1`.

Curl smoke tests:

```
GET http://localhost:3000/      -> 404   (no root handler — by design)
GET http://localhost:3000/me    -> 401   {"error":{"code":"UNAUTHENTICATED","message":"Unauthorized"}}
GET http://127.0.0.1:5173/      -> 200   (Vite serves index.html)
GET http://127.0.0.1:5173/collections -> 200  (Vite SPA fallback)
```

Playwright MCP navigated to `http://127.0.0.1:5173/`. The SPA redirected to `/collections`, `ProtectedRoute` checked `userManager.getUser()`, found nothing, and called `userManager.signinRedirect()`. The browser landed on:

```
https://dev-yg.us.auth0.com/authorize?
  client_id=__set_in_local_env__
  redirect_uri=http://localhost:5173/callback
  response_type=code
  scope=openid+profile+email
  state=5c9fee4ec0c0429fae1e43d7fa0b5b0e
  code_challenge=MxNd7cuSpS_kJPLNGnDyRoNSzfFRNHvO844fmRQyj_E
  code_challenge_method=S256
  audience=https://bbl-candidate-test-api
```

Auth0 returns HTTP 400 because `client_id=__set_in_local_env__` is a placeholder. With the real SPA client_id, the same URL would render the Auth0 login form. With the test user `candidate@test.com` / `@password1234` we'd then complete the round-trip and land back on `/collections` with a valid `code` to exchange for tokens.

This proves:
- The frontend boots and serves correctly.
- `/` → `/collections` redirect works.
- ProtectedRoute correctly identifies an unsigned-in state.
- PKCE is computed correctly (43-char base64url SHA256, `code_challenge_method=S256`).
- The `audience` parameter is sent (which is what gets Auth0 to mint a JWT access token for the API audience — without this, Auth0 would mint an opaque access token and our `JwtStrategy` couldn't validate it).
- The `redirect_uri` matches the one Auth0 has registered (would need to be configured in the Auth0 Application's "Allowed Callback URLs").

## What needs the real Auth0 client_id

To complete the round-trip with a real token, someone needs to:
1. Create the SPA Application in the Auth0 tenant (or use one that's already there) and obtain the `client_id`.
2. Configure the SPA Application's "Allowed Callback URLs" to include `http://localhost:5173/callback`.
3. Configure the API (audience `https://bbl-candidate-test-api`) in the tenant and authorise the SPA to request it. *(The brief says the audience is available; this should already be set up.)*
4. Set `VITE_AUTH0_CLIENT_ID` in `frontend/.env`.
5. Restart Vite.
6. Visit `http://localhost:5173/`, sign in with `candidate@test.com` / `@password1234`, observe redirect back to `/collections` with at least one collection visible (the user has alice-seed's data; or you can create one to test the create flow).

The PKCE shape above is the proof that the auth flow is wired correctly. Everything downstream of "we have a valid token" is already covered by the 17 e2e tests in `backend/test/privacy.e2e-spec.ts`.
